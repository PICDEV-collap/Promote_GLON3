# ตรวจประสิทธิภาพและความปลอดภัย — 2 ตุลาคม 2569

ขอบเขต: โค้ดที่ commit 0b370cf, บันทึกออเดอร์ในเครื่อง, ชุดทดสอบแบบแยกจากระบบจริง, npm production dependency audit และ HTTP health check แบบอ่านอย่างเดียว ไม่สร้างออเดอร์ ไม่ส่งข้อความทดสอบ ไม่เปลี่ยนโค้ดระบบ และไม่เปิดบอทที่หยุดอยู่ขึ้นใหม่

## สถานะและประสิทธิภาพ

- ขณะตรวจ พอร์ต 3333 ปฏิเสธการเชื่อมต่อ (`ECONNREFUSED`) ทั้งในการตรวจปกติและการตรวจนอก sandbox เบราว์เซอร์ CDP 9222 ยังตอบสนองและอยู่หน้า landing สาเหตุที่บอทหยุดยังไม่ได้ยืนยัน
- การตรวจ Tunnel รายงาน UNREACHABLE ยังแยกไม่ได้ว่าเกิดจาก tunnel เองหรือบอทปลายทางที่หยุดอยู่
- บันทึกหลังปรับการกดค้นหา: ออเดอร์ 6 เลขใช้ 11.0 และ 12.6 วินาที; 12 เลขใช้ 12.5 วินาที เทียบกับออเดอร์ 6 เลขก่อนปรับ 33.0 วินาที เป็นหลักฐานจากคนละออเดอร์ ไม่ใช่ benchmark ภายใต้สภาวะเดียวกัน และไม่ใช่ค่ารับประกัน

## Findings เรียงตามผลกระทบ

### 1. ต้องกำหนดขอบเขตความเชื่อถือของ IP จาก proxy

ตำแหน่ง: `bot-service/src/guard/cyber-guard.ts:236`, `bot-service/src/index.ts:2368`

`extractClientIp` ยอมรับ cf-connecting-ip, x-real-ip และ x-forwarded-for ก่อนตรวจ socket ของผู้ส่ง ขณะที่ server.listen ไม่กำหนด host การทดสอบในหน่วยความจำยืนยันว่าผู้ส่งจาก IP ภายนอกสามารถทำให้ระบบรายงาน IP เป็น localhost ได้

ผลกระทบ: หากเข้าถึง origin โดยตรงได้ ผู้ส่งสามารถเปลี่ยน IP ที่ใช้จำกัดคำขอและหลบการแบน IP ได้ การเข้าถึง origin จากภายนอกจริงยังไม่ได้ยืนยัน ต้องตรวจ firewall และเส้นทาง proxy เพิ่ม

แนวทาง: ถ้า Cloudflare Tunnel เป็นช่องทางเดียว ให้ bind บอทกับ loopback; เชื่อถือเฉพาะ header ที่ proxy ที่กำหนดเป็นผู้สร้าง ตรวจรูปแบบ IP และไม่ใช้ x-forwarded-for จากผู้ส่งทั่วไปเป็นตัวตน

### 2. ตัวจำกัดคำขอขัดกับการเช็กสถานะปกติของลูกค้า

ตำแหน่ง: `bot-service/src/guard/cyber-guard.ts:355`, `order.html:3157`, `order.html:3266` และหน้าสั่งซื้อสำเนา

เว็บเช็กสถานะทุก 1.5 วินาที (40 ครั้ง/นาที) แต่ `/api/order*` ใช้ limit ร่วม 30 ครั้ง/นาที ทั้งสร้างออเดอร์และเช็กสถานะ การทดสอบ middleware แบบแยกยืนยันว่า 40 คำขอผ่าน 30 และถูกปฏิเสธ 10

ผลกระทบ: ออเดอร์ที่ใช้เวลานานหรือผู้ใช้เปิดหลายหน้าจะถูก 429 แม้ใช้งานปกติ ฝั่งเว็บ `if (!statusRes.ok) return` ข้ามการตรวจ timeout ในรอบที่ผิดพลาดด้วย จึงอาจค้างนานกว่าที่ตั้งไว้

แนวทาง: แยก limit สำหรับอ่านสถานะออกจากการสร้างออเดอร์ เคารพ Retry-After ไม่ให้คำขอ polling ซ้อนกัน และใช้ deadline ตามเวลาจริงที่ทำงานแม้ได้รับ HTTP error

### 3. แพ็กเกจใช้งานจริงมีรายการช่องโหว่ระดับปานกลาง

ติดตั้ง: qs 6.15.3, express 4.22.2, body-parser 1.20.6

npm audit --omit=dev รายงาน 3 แพ็กเกจระดับ moderate, high/critical เป็น 0 โดยสองแพ็กเกจได้รับผลสืบทอดจาก qs ไม่ใช่สามช่องโหว่อิสระ ผลกระทบเป็นความพร้อมใช้งานตามเงื่อนไขใน advisory ไม่ได้ยืนยันว่าช่องโหว่ถูกโจมตีผ่านแอปนี้ได้ทุกกรณี

แหล่งข้อมูล:
- https://github.com/advisories/GHSA-4mjr-xmp4-gh2g
- https://github.com/advisories/GHSA-x5fp-wj9c-mxmx

แนวทาง: อัปเดตแพ็กเกจในขอบเขตเวอร์ชันที่เข้ากันได้ แล้วรัน audit และชุดทดสอบใหม่ก่อนเปิดใช้

### 4. QR Login และภาพวิเคราะห์ข้อผิดพลาดอยู่ใน static directory สาธารณะ

ตำแหน่ง: `bot-service/src/automation/n3-auth.ts:172`, `bot-service/src/index.ts:208-215`

ชื่อ QR Login อาศัยเวลา timestamp; static /qrcodes ส่ง Cache-Control public 24 ชั่วโมง และไฟล์เดียวกันอาจเข้าถึงผ่าน /public/qrcodes ได้ด้วย ภาพ error อยู่ใน directory เดียวกัน

ผลกระทบ: ผู้ที่ทราบ URL สามารถอ่านภาพได้โดยไม่ตรวจสิทธิ์ แม้ QR จะหมดอายุใน GLO แล้วไฟล์ยังอาจถูกดาวน์โหลดได้ ภาพผิดพลาดอาจมีข้อมูลร้านค้า การได้ภาพ QR อย่างเดียวไม่ได้พิสูจน์ว่าจะเข้าบัญชีร้านได้สำเร็จ

แนวทาง: ใช้ชื่อสุ่มที่คาดเดาไม่ได้ ปิดเส้นทางสำเนาสำหรับไฟล์อ่อนไหว ใช้ TTL สอดคล้องกับ QR และ no-store สำหรับ QR Login แยกภาพ error จาก public directory โดยยังรองรับการโหลดภาพของ LINE

### 5. ไม่มีขีดจำกัดจำนวนออเดอร์รวมในคิว

ตำแหน่ง: `bot-service/src/queue/order-queue.ts:50`, `bot-service/src/index.ts:860`, `bot-service/src/index.ts:959`

การสั่งผ่านเว็บแบบ anonymous เป็นพฤติกรรมที่ตั้งใจรองรับอยู่แล้ว แต่คิวไม่มีเพดานรวม ไม่มี idempotency ของคำขอซ้ำ และใช้ RAM เป็นหลัก Limit ต่อ IP ช่วยได้บางส่วนแต่ไม่ใช่ขีดจำกัดรวม

ผลกระทบ: คำขอจำนวนมากจากหลายแหล่งหรือการกดย้ำทำให้เวลารอและหน่วยความจำเพิ่ม; รีสตาร์ตจะสูญเสียออเดอร์ที่อยู่ใน RAM

แนวทาง: เพิ่มเพดานคิวและตอบ busy อย่างชัดเจน จัดการคำขอซ้ำ และเพิ่มการเก็บออเดอร์ที่กู้คืนได้ โดยรักษาการสั่งซื้อปกติให้ใช้ง่าย

### 6. สถานะออเดอร์ที่ไม่มีอยู่ถูกตอบว่าอยู่ในคิว

ตำแหน่ง: `bot-service/src/queue/order-queue.ts:110-118`, `bot-service/src/index.ts:815`

getPosition คืน 1 เมื่อไม่พบออเดอร์ แต่ order-status ใช้ค่า > 0 เพื่อรายงาน queued จึงทำให้สาขา 404 สำหรับออเดอร์ที่ไม่รู้จักทำงานไม่ตรงเจตนา

แนวทาง: คืน 0 เมื่อไม่พบ เพิ่ม regression test ให้ order-status ตอบ 404 สำหรับออเดอร์ที่ไม่อยู่ทั้ง store และ queue

## สิ่งที่ตรวจผ่าน

- Build TypeScript สำเร็จ
- ชุดทดสอบหลัก 123/123 ผ่าน
- ชุดทดสอบ process ownership และ tunnel 13/13 ผ่าน
- ทดสอบ loader/disabled search control, การรักษาพิกัด และ expired-home login recovery ผ่าน
- สแกนไฟล์ที่ Git ติดตาม 3,472 ไฟล์: ไม่พบข้อมูลลับตามรูปแบบของ scanner ผลนี้ไม่ยืนยันว่าปราศจากข้อมูลอ่อนไหวทุกประเภท
- ตรวจโค้ดพบ API แอดมินใช้ timingSafeEqual, Webhook ตรวจ LINE signature, จำกัด body 256 KB, ปิด x-powered-by และมี static whitelist

ข้อจำกัด: ยังไม่ได้ทดสอบ HTTP authorization/header ของระบบที่รันจริงเพราะบอทไม่ตอบสนอง; ไม่ได้ทำ load test บน production, จำลองโจมตีทางเครือข่ายจริง หรือทดสอบ firewall จากภายนอก

ลำดับถัดไป: ยืนยันเหตุที่บอทไม่ตอบสนอง แล้วแก้ polling/limit, proxy-IP trust และแพ็กเกจ ก่อนตรวจ QR retention กับเพดานคิว ไม่ควรสรุปว่าระบบปลอดภัยทั้งหมดจากผล unit test เพียงอย่างเดียว

## ผลปรับปรุงภายหลังได้รับอนุญาต

- เปิดบอทของโปรเจกต์นี้โดยยืนยันเจ้าของพอร์ตก่อน ไม่มีการหยุดโปรเซสหรือยึดพอร์ตของโปรเจกต์อื่น บอท bind เฉพาะ 127.0.0.1; launcher ใช้ tunnel origin แบบ IPv4 ชัดเจน
- ทดสอบจริง health ในเครื่องและผ่าน public tunnel ได้ HTTP 200
- รับ cf-connecting-ip เฉพาะเมื่อ socket มาจาก loopback และเป็น IP ที่ถูกต้อง ไม่รับ x-real-ip/x-forwarded-for จากผู้ส่งทั่วไป
- แยกเพดาน status polling เป็น 120 ครั้ง/นาที การสร้างคำสั่งซื้อยังจำกัดต่างหาก ฝั่งเว็บมี Retry-After, fetch timeout, deadline ตามเวลาจริง และไม่ส่ง poll ซ้อนกัน
- คิวไม่เกิน 100 ออเดอร์; คำขอเว็บมี clientRequestId ป้องกันการสร้างออเดอร์ซ้ำในหน่วยความจำเป็นเวลา 30 นาที; ออเดอร์ไม่รู้จักตอบ 404 แล้ว
- QR Login ใช้ UUID, no-store และตัดการเข้าถึงหลัง 5 นาที; ปิดไฟล์ผ่าน /public/qrcodes และ download-qr สำหรับ login QR; ภาพ error ใหม่เก็บใน data/diagnostics
- อัปเดต express 4.22.3, qs 6.16.0 และ dependencies ที่เกี่ยวข้อง; npm audit ไม่พบรายการช่องโหว่
- ทดสอบจริง: QR Login ชื่อแบบเก่า, ภาพ error และ public path สำเนาตอบ 404; download ของ login QR ตอบ 400; admin API ตอบ 503 เนื่องจากไม่ได้ตั้ง ADMIN_API_KEY ซึ่งเป็นการปิดใช้งานตามค่าเริ่มต้น

ขอบเขตที่ยังคงเหลือ: คิวและ cache ป้องกันคำขอซ้ำยังอยู่ใน RAM ไม่ใช่ระบบกู้คืนออเดอร์ถาวร การเพิ่ม persistent queue ต้องออกแบบการยืนยันสถานะจาก GLO ก่อน replay เพื่อไม่สร้างรายการซ้ำหลังรีสตาร์ต ยังไม่ได้บังคับ logoff เซสชันจริงเพื่อทดสอบ login QR และไม่ได้สร้างออเดอร์ลูกค้าทดสอบระหว่างการปรับปรุง
