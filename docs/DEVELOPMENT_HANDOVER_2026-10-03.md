## 3. สิ่งที่แก้ไขแล้ว แยกตามระบบ

### 3.1 การเข้าสู่ระบบ GLO และการขอ QR login

- ปรับการกู้สถานะเซสชันและการขอ QR login เมื่อ GLO logoff เพื่อลดการตีความว่าเซสชันหลุดผิดจังหวะและวงจรรอ QR ที่ไม่จบ
- ตรวจสภาพหน้าและโหลดหน้าแทนการรอคงที่ในบางจุด ลดเวลารอระหว่างค้นหาและเลือกเลข
- QR login ใช้ชื่อสุ่ม UUID พร้อมข้อกำหนดไม่ cache และหมดอายุการเข้าถึงหลัง 5 นาที
- ภาพวิเคราะห์ข้อผิดพลาดเก็บแยกจากภาพ QR ที่เผยแพร่สาธารณะ
- ผู้ดูแลอนุญาตให้ refresh GLO หรือ restart bot เมื่อค้าง แต่ต้องรักษาตะกร้า เซสชัน และพอร์ตของโปรเจกต์อื่น

ข้อจำกัด: การทดสอบที่บันทึกไว้ไม่ได้บังคับ logoff ระบบจริงเพื่อยืนยันทุกกรณี recovery จึงยังต้องทดสอบในช่วงที่ไม่มีออเดอร์ลูกค้าค้าง

### 3.2 การเลือกเลข จำนวนใบ และตะกร้า GLO

- ลดความช้าของการค้นหาและเลือกเลข โดยตรวจการเปลี่ยนสถานะหน้าแทนการเพิ่มเวลารอแบบตายตัว
- แก้การเพิ่มจำนวนซ้ำ: กรอกจำนวนและตรวจค่าจริงก่อนเพิ่มอีกครั้ง
- แก้การตีความข้อกำหนด input ของ GLO เป็นเพดานเพียง 3 ใบ ซึ่งเคยทำให้คำขอเลขเดียว 60 ใบถูกปฏิเสธผิด
- เปลี่ยนการตรวจจำนวนจากการดูการ์ดค้นหาครั้งล่าสุด เป็นตรวจตะกร้าทั้งออเดอร์จาก `cart-store` และเทียบเลข/จำนวนกับรายการที่ต้องส่ง
- ตรวจข้อความจำกัดสูงสุด 100 ใบจาก GLO เพื่อรายงานสาเหตุแทนการรอจน timeout
- จำกัดรวม 100 ใบตั้งแต่ขั้นเลือกเลขและก่อนเข้าคิว ทำให้คำขอเกินเพดานไม่ไปค้างบน GLO
- ทำชื่อไฟล์ QR ให้สั้นสำหรับออเดอร์หลายเลข ลดปัญหาชื่อไฟล์ยาวเกิน

ตัวอย่างการนับ: 18 ชุด × 6 เลขกลับ × 1 ใบ = 108 ใบ ถ้ามีเลขซ้ำข้ามชุดอาจเหลือ 96 เลขไม่ซ้ำ แต่ยังมี 108 ใบ จึงต้องบล็อกตามเงื่อนไขล่าสุด

### 3.3 โควต้าและหน้าที่ค้าง

- แยกการอ่านโควต้าไปหน้าเฉพาะ ไม่เปลี่ยนหน้า GLO ที่ใช้ดำเนินออเดอร์อยู่
- ส่งข้อมูลยืนยันเซสชันที่จำเป็นไปหน้าอ่านโควต้า โดยไม่คัดลอกตะกร้า
- รวมคำขออ่านพร้อมกันเพื่อลดการเปิดงานซ้ำ และปิดหน้าอ่านหลังเสร็จ
- ปรับการอ่านข้อมูลใหม่จาก landing เป็นช่วงเมื่อไม่มีงานสั่งซื้อ เพื่อลดปัญหาข้อมูลเก่าค้าง

ผลที่ต้องรักษา: การอัปเดตโควต้าต้องไม่พาบอทออกจากหน้าสั่งซื้อกลางออเดอร์ ไม่ควรแก้ด้วยการ refresh ทุกหน้าโดยไม่ตรวจว่าออเดอร์กำลังทำงานหรือไม่

### 3.4 หน้าเลือกเลขและสูตรเลขกลับ

- เลือกบางเลขจากชุดเลขกลับได้ ไม่บังคับซื้อครบทุกเลข
- จำนวนใบแยกตามเลข เช่น `127 = 2 ใบ`, `172 = 1 ใบ` ได้
- รวมยอดตามจำนวนใบจริง พร้อมเตือนเมื่อเกินเพดานและปิดการยืนยัน
- ปรับการ์ด ช่องกรอก และปุ่มเพิ่ม/ลดบนมือถือให้เป็นระเบียบและไม่ล้นแนวนอน
- ล้างรายการ คำสั่งซื้อ QR และตัวจับเวลาหลังเสร็จสิ้นหรือออกจากหน้า โดยไม่ล้างข้อมูลระบุตัวตนที่ใช้ต่อได้

### 3.5 LINE และ Telegram

- ฟื้นการส่ง LINE access token จากหน้าสั่งซื้อไปยังเซิร์ฟเวอร์
- ตรวจ token และ channel/audience ที่เซิร์ฟเวอร์ ไม่เชื่อถือ user ID ที่หน้าเว็บส่งมาเอง
- Telegram แสดงชื่อเมื่อมีข้อมูล พร้อม LINE user ID เต็มและ order ID เพื่อใช้ตามปัญหา
- แยกออเดอร์ทดสอบของแอดมินจากบัญชี LINE ที่ยืนยันแล้วเท่านั้น
- ออเดอร์ที่ไม่มีตัวตนยืนยันต้องแสดงว่าไม่ทราบตัวตน ไม่ตั้งชื่อหรือระบุว่าเป็นแอดมินโดยเดา

ข้อควรทราบ: API ยังมีเส้นทางรองรับคำขอเว็บที่ไม่มี token เพื่อความเข้ากันได้ ส่วนหน้าสั่งซื้อปัจจุบันขอ token ก่อนส่งคำสั่งซื้อ การบังคับทุกช่องทางต้องมี token ยังไม่ใช่สิ่งที่เสร็จแล้ว

### 3.6 การเปิดหน้า ออกจากหน้า และบันทึก QR

- Rich Menu สั่งซื้อปกติ: `https://liff.line.me/2011462211-WVsuHFk4/line`
- Rich Menu สูตรเลขกลับ: `https://liff.line.me/2011462211-WVsuHFk4/line?mode=6pack`
- เลิกบังคับหน้าสั่งซื้อออกไป external browser เพื่อให้ LIFF ปิดหน้าได้
- เนื่องจาก endpoint ที่ลงทะเบียนไว้เริ่มจาก root จึงเริ่ม LIFF ก่อนแสดงเนื้อหาหน้าหลัก และซ่อนหน้าหลักระหว่างส่งต่อไป `/line`
- มีกฎ rewrite สำหรับ `liff.state` แต่การตรวจหลัง deploy พบว่า root ยังส่ง HTML หน้าหลัก จึงใช้ตัวป้องกันการแสดงหน้าหลักใน `index.html` เป็นกลไกที่ตรวจยืนยันแล้ว ไม่ควรถือว่า rewrite เพียงอย่างเดียวแก้ได้
- ปุ่มเสร็จสิ้นล้างข้อมูลแล้วเรียก `liff.closeWindow()` ใน LINE; เบราว์เซอร์ภายนอกอาจไม่อนุญาตให้สคริปต์ปิดแท็บ
- นำปุ่มกลับหน้าแรกและข้อความชวนเปิด Chrome/Safari ออก
- เคยเพิ่มตัวช่วยบันทึก QR เพราะ Android LINE ไม่ตอบสนองต่อการดาวน์โหลด Blob; ต่อมาผู้ใช้ให้เอาปุ่มบันทึก QR ออก จึงเปลี่ยนขั้นตอนลูกค้าเป็นแตะค้าง/แคปหน้าจอแทน
- คำแนะนำปัจจุบันบอกวิธีบันทึกภาพ ตำแหน่งที่จะพบภาพ การเลือกรูปในเป๋าตัง และให้ชำระก่อนเวลานับถอยหลังหมด

ข้อจำกัด: ยังไม่มีผลทดสอบครบถ้วนบน Android/iPhone จริงทุกรุ่น การแตะค้างขึ้นอยู่กับ LINE และระบบปฏิบัติการ จึงมีแคปหน้าจอเป็นทางเลือก ส่วน utility บันทึกภาพยังอยู่ในโค้ด ไม่ได้หมายความว่ามีปุ่มให้ลูกค้ากดในหน้าผล QR แล้ว

### 3.7 ประสิทธิภาพและความปลอดภัย

- บอท bind เฉพาะ loopback `127.0.0.1` และรับ proxy IP header เฉพาะจากเส้นทางที่กำหนด
- แยก rate limit สร้างออเดอร์ออกจากอ่านสถานะ; polling สูงสุด 120 ครั้ง/นาที
- หน้าเว็บไม่ poll ซ้อน มี fetch timeout, Retry-After และตรวจ deadline แม้เกิดข้อผิดพลาด
- จำกัดคิวไม่เกิน 100 ออเดอร์ ซึ่งเป็นคนละเพดานกับ 100 ใบต่อออเดอร์
- ใช้ `clientRequestId` ป้องกันคำขอซ้ำในหน่วยความจำ 30 นาที; order ID ที่ไม่รู้จักตอบ 404
- จำกัดการเผยแพร่ QR login และภาพ error ผ่าน public path
- ปรับแพ็กเกจที่เกี่ยวข้องกับผลตรวจ dependency และใช้ pre-commit ตรวจข้อมูลลับ

ผล audit ที่บันทึกในวันที่ตรวจไม่มีช่องโหว่จาก dependency audit แต่ไม่ใช่ผลตรวจความปลอดภัยทั้งหมด และต้องตรวจซ้ำเมื่อติดตั้ง/อัปเดตแพ็กเกจ

ระวัง `scripts/setup-richmenu.js`: workflow ปัจจุบันมีการลบเมนูเดิม จึงไม่ควรรันเพียงเพื่อแก้ลิงก์สองปุ่ม ให้ใช้เครื่องมือที่รักษาเมนูเดิมและตรวจรายการก่อนเปลี่ยน

## 5. หลักฐานการตรวจและสิ่งที่ยังไม่ยืนยัน

| สิ่งที่ตรวจแล้วในงานที่ผ่านมา | ขอบเขตของหลักฐาน |

| LIFF และปุ่มออก | ทดสอบเส้นทาง โหมด และการล้างข้อมูลด้วย browser automation และ SDK จำลอง |

ยังต้องทดสอบ: LINE บน Android/iOS จริง, บันทึกภาพ/แคปและเลือกรูปในเป๋าตัง, ออกจาก LIFF จริง, ออเดอร์เต็มเพดานในช่วงไม่มีลูกค้ารอ และการกู้คืนหลังเซสชันหลุด ไม่ได้ทำ production load test หรือยืนยันสถานะบริการสดใหม่ในวันที่จัดทำเอกสาร

เวลาที่บันทึกเคยพบออเดอร์ 6 เลขลดจากประมาณ 33 วินาทีเหลือ 11–12.6 วินาที และ 12 เลขประมาณ 12.5 วินาที เป็นคนละออเดอร์และคนละสภาพการทำงาน ไม่ใช่ benchmark ควบคุมหรือค่ารับประกัน

### ชุดตรวจสำหรับงานครั้งถัดไป

เลือกชุดทดสอบตามส่วนที่แก้ ไม่จำเป็นต้องรันทุกชุดสำหรับการเปลี่ยนข้อความเล็กน้อย

```powershell
# เมื่อแก้โค้ดบอท
npm run build --prefix bot-service

# จำนวนสลากและสูตรเลขกลับ
node --test scripts/test-selection-limit.js scripts/test-permutation-selection.js scripts/test-cart-audit.js scripts/test-portal-quantity.js scripts/test-large-order-qr.js

node --test scripts/test-order-line-token.js scripts/test-telegram-order-identity.js scripts/test-security-hardening.js

```

utility รูปภาพที่ทดสอบไว้ไม่ได้แทนการทดสอบว่ามือถือจริงสามารถบันทึกภาพจากหน้าปัจจุบันได้ ห้ามรันสคริปต์สั่งซื้อจริงหรือส่งข้อความจริงโดยคิดว่าเป็น unit test

## 6. ลำดับพัฒนาต่อที่แนะนำ

| ลำดับ | งาน | เงื่อนไขผ่านก่อนถือว่าเสร็จ |
|---|---|---|
| P0 | ทดสอบลูกค้าจริง Android/iOS | ทั้งสองเมนูเปิดถูกโหมด ไม่แสดงหน้าหลักก่อน บันทึก/แคป QR และออกจาก LIFF ได้ |
| P0 | เก็บเหตุการณ์ออเดอร์เป็นช่วง | มี order ID, เวลาเข้าคิว/ค้นหา/ปรับจำนวน/สร้าง QR, สาเหตุล้มเหลว และรุ่น deployment โดยไม่เก็บ token |
| P0 | Recovery เมื่อ GLO ค้าง | ตรวจงานที่กำลังทำก่อน refresh/restart; ไม่สร้างออเดอร์ซ้ำ และไม่แตะโปรเซสอื่น |
| P1 | คิวถาวรและป้องกันซ้ำหลัง restart | ตรวจสถานะบน GLO ก่อน replay; กู้รายการค้างได้โดยไม่ซื้อซ้ำ |
| P1 | เหลือแหล่งโค้ดหน้าสั่งซื้อชุดเดียว | ใช้ template/build สร้างสำเนา ลดการแก้หกไฟล์ไม่ตรงกัน |
| P1 | จัดการอายุ QR ชำระเงิน | กำหนด retention, cache และการลบภาพให้ชัด แยกจาก QR login |
| P1 | ทำเส้นทาง LIFF ให้ตรง endpoint | ทบทวนการตั้งค่า LINE Console และทดสอบ token/login/close ใหม่ก่อนเปลี่ยน |
| P2 | วัดประสิทธิภาพแบบควบคุม | เปรียบเทียบ 1, 6, 30, 60 และ 100 ใบ พร้อมจำนวนเลขที่ต่างกัน โดยไม่เกินเพดานจริง |
| P2 | ตรวจความปลอดภัยรอบถัดไป | ตรวจ dependency, origin/proxy, anonymous API และการเก็บข้อมูลลูกค้า |

คิวและ cache ป้องกันคำขอซ้ำยังอยู่ใน RAM การ restart จึงมีข้อจำกัดด้านการกู้คืน ห้ามแก้ด้วยการส่งทุกออเดอร์ค้างซ้ำโดยไม่ตรวจ GLO

## 7. ขั้นตอนส่งงานครั้งถัดไป

1. ระบุปัญหา ตัวอย่างออเดอร์ และเงื่อนไขผ่านให้ชัดก่อนแก้
2. อ่าน log โดยใช้ order ID แยกปัญหาเว็บ บอท GLO และ tunnel
3. ตรวจเจ้าของพอร์ตและงานค้างก่อนแตะบริการที่รันอยู่
4. แก้ต้นฉบับและสำเนาที่เกี่ยวข้อง พร้อมทดสอบส่วนที่เปลี่ยน
5. Commit เฉพาะไฟล์งาน ตรวจข้อมูลลับ แล้ว push
6. หน้าเว็บ: รอ deployment พร้อมและตรวจโดเมนใช้งานจริง; บอท: build และเปิดรุ่นใหม่อย่างปลอดภัยเมื่อไม่มีงานค้าง
7. ตรวจ health, public API และเส้นทางลูกค้า โดยแยกผลทดสอบจำลองกับผลจากมือถือจริง
8. บันทึก commit, การเปลี่ยนพฤติกรรม, ผลทดสอบ และข้อจำกัดลงเอกสารส่งต่อ
